# 08: Player provenance — nationality, birthplace, and nation-keyed names

**What to build:** a player has an origin. Their profile shows a nationality and a birthplace, a
squad in a Portuguese league reads like a Portuguese squad rather than an English one, and foreign
players appear in a squad in proportion to the recruitment links the nation profile describes. A
full name recurs about as often as it does in a real league, so four hundred thousand players do not
read as four hundred people.

The same person stays the same person across careers: because the geography catalogue is
unconditional, a player with a given id has the same birth city whichever nations the player
selected. The birthplace column stays nullable and means "born outside the loaded world" — an escape
hatch for a catalogue nation whose geography is not yet curated — but no player generated by MVP
carries a NULL.

Name pools live in code beside the nation profiles as factual, nation-keyed data, not in the content
pack: a pack ships before the players it would have to name, so names are stored directly on the
player as an attribute beside the identifier. Today's pool is 400 global combinations and must grow
to roughly 20,000 per nation; this ticket ships the nation-keyed structure and the recurrence test,
and growing the pools is content work behind that test.

Exactly one nationality exists, with the reintroduction condition recorded rather than left to a
later reader's judgement: a second nationality returns only when work permits or national teams
ship. No career-history table ships here; career history is ticket 17's transfer rows.

The slice's edge promise: name drawing is a pure function of a seed and a nation, so it adds no
failure to generation's error channel. A nation with an empty name pool is a defect in the shipped
data caught by a test over the module.

**Decisions:**

- One nationality with a stated reintroduction condition, a nullable `birth_city_id` whose NULL
  means "born outside the loaded world", nation-keyed name pools in code as factual data (today's
  pool is 400 combinations and must grow), names stored directly because a pack cannot name players
  it predates, and no career-history table because the event log already holds it. See
  [Agent Note](../../../.agents/notes/implemented/architecture/2026-09-01-player-provenance-and-nationality.md).
  The career-history clause is superseded by ticket 17, which ships `player_transfers` as
  authoritative state.
