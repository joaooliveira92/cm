## Problem Statement

The `@cm-clone/desktop` renderer has no visual design language informed by the CM 03/04 reference at `docs/ui-elements.md`. All nine screens render a flat dark slate (`bg-slate-950`) with default Tailwind typography, no panel system, no status vocabulary, no persistent chrome, and no skin architecture - a generic, text-dense-but-flat surface that carries none of the retro identity the reference material specifies.

This is not a greenfield problem. A visual frame was adopted on 2026-08-29 and then **sat unbuilt** while flat-slate styling spread further: exactly 391 hardcoded `slate-*` call sites sit across 25 files today. The decision did not fail because it was wrong; it failed because nothing said how to apply it to a tree that was already styled. A spec that only says what the UI should look like reproduces that failure. It must also say how to get there from here.

## Solution

Ship the renderer a coherent **retro chrome-blue visual frame**: a role-named token system (dark base, chrome-blue gradients, semi-transparent panel surfaces, Trebuchet MS typography, compact density), a two-row career chrome (gradient title bar with club identity and the date/Continue cluster; a restyled tab strip beneath), a dense shared-table vocabulary including a reserved player-status column, a match day that renders inside that same chrome, and a non-table layout grammar (fields, dialogs, creation-flow frame, empty/error states) - so every surface in the game announces the same voice.

That look lands through an **incremental adoption path**, not a big-bang restyle: the whole renderer repaints atomically and reversibly via a `slate-*` alias layer, then shared-layer-first renames move call sites onto semantic tokens under a stable palette, with a lint guard live from the first commit so flat slate can never spread again. The adopted frame finally builds.

## User Stories

### The look

1. As a manager playing a career, I want the whole game to share one visual identity, so that changes of screen never feel like I switched to a different product.
2. As a manager, I want the dark chrome-blue surfaces and semi-transparent panels it is modeled on, so that the game reads retro rather than generic.
3. As a manager, I want compact, text-led panels with a shared surface, border, and shadow, so that every content area looks deliberate rather than ad hoc.
4. As a manager, I want dense 12px table rows, so that I can read many players on screen at once the way CM 03/04 did.
5. As a manager, I want the page background to stay a single dark gradient, so that content panels keep readable contrast rather than competing with per-screen imagery.
6. As a manager, I want text-led icons (unicode and CSS marks only), so that the UI stays dense and readable instead of icon-cluttered.

### The career chrome, Continue, and temporal state

7. As a manager, I want a persistent gradient title bar showing my club's name on the left, so that my club context is visible on every career screen.
8. As a manager, I want a season readout (`Season n · Matchday m/38`) with phase words (Pre-season, Transfer window open, Season complete) and my save name, so that I always know where in the career I am without a date - the Calendar has no day-by-day clock.
9. As a manager, I want one always-visible Continue in the chrome's right cluster, so that the game's core rhythm (inspect, decide, continue) is reachable from every career screen.
10. As a manager, I want the effective key binding shown on the Continue button and its reason when it is disabled, so that I never face a button that is unavailable without explanation.
11. As a manager, I want the active career tab to read as the framed locus (gradient-inverted), so that I can tell at a glance which section I am in.
12. As a manager, I want "Back to saves" to read as a chrome control distinct from section tabs, so that leaving the career never looks like navigating a section.
13. As a manager, I want the tab strip to scroll with arrow affordances once sections outgrow the strip, so that every section stays reachable by focus and quick key even when it is out of view.
14. As a manager, I want my screen headings to carry the section name only, with the club living in the title bar, so that headings do not duplicate context.
15. As a manager on a match day, I want the chrome's temporal cluster to show the match readout while the match is live and return to the season readout + Continue at full time, so that one primary verb is on screen at any moment.

### Dense tables and the status vocabulary

16. As a manager, I want table rows at the compact density with flat divider headers and a subtle sort indicator, so that a 30-column squad reads cleanly and sorts are visible at 12px.
17. As a manager, I want hover, selection, and focus to look different from one another and from the focus ring, so that I never mistake row selection for keyboard focus.
18. As a manager, I want the horizontal-scroll edge signalled by a soft fade, so that I know when more columns exist beyond the visible width.
19. As a manager, I want a pinned Status column right of the player name that is always visible, even when I scroll the attribute columns or toggle column visibility, so that a player's state never scrolls out of view.
20. As a manager, I want the Status column to show exactly what the engine models (today condition) and nothing invented, so that a displayed status can always be trusted.
21. As a manager, I want statuses rendered as CM-style three-letter abbreviations coloured by the existing danger/warning/success semantics, so that I scan them quickly the way I would in the original.
22. As a keyboard or screen-reader player, I want the full term spoken when a row gains focus, never the raw abbreviation, so that the vocabulary is accessible to non-visual reading.
23. As a keyboard or screen-reader player, I want the full abbreviation legend accessible from the Status column's header (Term Disclosure pattern, never hover-only), so that every reserved status can be looked up without a mouse.

### Match day

24. As a manager, I want the match-day screen to live inside the same career chrome and token system as the other screens, so that a live match feels like the career rather than a separate product.
25. As a manager, I want the stadium cue rendered as a CSS-only wash under a dark overlay, so that match day feels immersive without needing image assets.
26. As a manager, I want a neutral chrome-band scoreboard with white score boxes and the two club names flanking the score, so that the result is the archetypal match-day picture.
27. As a manager, I want the commentary feed to carry a minute gutter and incident colours drawn from the shared semantic tokens, so that incident types read at a glance within one palette.
28. As a manager, I want possession, incidents, and fixture panels left unbuilt until the engine exposes their data, so that no visual guesses at schema.

### Fields, dialogs, the creation flow, and empty/error states

29. As a player creating a career, I want a light gradient chrome band with an in-band "Step N of 4" indicator and Cancel/Back, so that the flow feels like the same product with a clear sense of progress.
30. As a player, I want form fields to share one pattern (opaque field surface, thin rim, single focus ring, 12px labels), so that league lists, text inputs, and manager forms look consistent.
31. As a player, I want checkbox accents to match the primary-action language rather than a second hue, so that there is no competing accent colour.
32. As a player, I want every overlay (quit-confirm, preferences, help, palette, confirmations) to share one modal anatomy - gradient title band, strong-panel body, scrim-click closing - so that dialogs never feel hand-copied or divergent.
33. As a keyboard or screen-reader player, I want modal keyboard behavior (Escape, tab trap, focus restore) unchanged by the restyling, so that the visuals never break the focus model.
34. As a manager, I want empty surfaces to render a muted, text-led line (with a "Clear all filters" action when filtering caused the emptiness), so that an empty area explains itself without noise or icons.
35. As a manager, I want structural failures to render a danger alert panel with a Retry action, and inline errors as a danger line under the field, so that error severity is visually proportional.

### Adoption, migration, and guardians

36. As an implementer, I want the whole renderer to repaint onto the adopted palette in one reversible change with zero JSX edits, so that two palettes never coexist on screen and the baseline can be reverted in a commit.
37. As an implementer, I want to consume tokens via generated utilities and shared class-string constants rather than a component library, so that the existing utility-composition idiom is preserved.
38. As an implementer, I want the migration sequenced shared-layer-first under a stable palette with each alias deletable once its last user renames, so that the source-level `slate-*` residue shrinks to zero predictably.
39. As the repo's gatekeeper, I want `pnpm check:all` to fail on any fresh `slate-*` class from the alias commit onward, so that flat slate cannot sprawl again after the frame is adopted.
40. As a future skin maintainer, I want token values re-declarable under a scope without re-writing utilities, so that a skin system (still deferred and gated) is cheap when a real second theme exists to judge.

## Testing Decisions

**What makes a good test here: assert external behavior, never implementation details.** The token and class-string composition is the mechanism, not the contract - a test that greps a `className` is testing the implementation. Renderer tests assert rendered semantics: accessible names and roles, action reachability, active-match state toggling, announced strings, and column presence. The pure-CSS look (palettes, gradients, density, borders) has no auto-test seam in this repo (no screenshot-regression harness exists) and the spec does not invent one: it is verified by the adoption acceptance criteria's diff plus a human visual pass at each migration step, with `pnpm check:all` green at every step.

**Seam 1 - renderer component tests through the career shell (the primary seam).** Behavioral contracts left by the visual decisions are tested the way the existing suite already tests career screens: render a screen under the shell with a mocked RPC and drive it.

- **Continue from every career screen**: the shell owns the handler; `Space` and the button dispatch from any career screen; the disabled state renders the action's reason. Prior art: `actions-inventory.test.tsx` (renders each career screen with active-match toggling and asserts action reachability), `discoveabilty-key-badges.test.ts`, `keyboard-spine-live.test.tsx`.
- **Tempaoral-cluster switching**: during a live match the cluster shows the match readout and Continue is unavailale; at full time it returns to the season readout + Continue. Prior art: `matchday-live-keyboard.test.tsx`, `match.test.ts`.
- **Status-column contract**: the Status column is always present and survives the visiility toggles and presets; unmodeled statuses render empty cells; the full term is fed to the polite announcer on row focus, never the abbreviaion. Prior art: `table-colum-prefences.test.ts`, `table-view-state.test.ts`, `table-sort-filter.test.ts`, and the `table-focus-*` tests.

Tests in this seam never asert which utility class strings a row or button carries - only the rendered semantics.

**Seam 2 - the `no-slate-class-name` lint rule (the mechaanical guard).** The rule lives in the effect-lint harness, and the harness already requires every fixture under its fixtures directory to trip at least one violation - so the rule gets a fixture that must fail, and the clean repository must pass. The 391-site baseline is the migration backlog; a fresh `slate-*` class fails `check:all` from the alias commit. Prior art: the existing `renderer-boundary` fixture and the harness's fixture contract.

**The visual modal, empty, and error patterns are seam-less by decision.** They are restrained by the visual pass, not by tests; the layout-grammar decision names prose enforcement as the risk and routes a third recurrence to a lint rule per the repo's routing discipline.

## Out of Scope

- **Keyboard interaction design.** Bindings, the focus model, and the Action registry are shipped and settled; this spec decides how those interactions *look* - focus rings, sort indicators, active-tab treatment - never how they behave.
- **Onboarding and career-creation flow logic.** The sequence of screens, the league selector's behaviour, and the manager-form rules are product decisions made elsewhere; this spec provides the visual shell they render in.
- **Authoring the CSS and React components.** Plan-only: this spec hands off to implementation and does not author renderer code.
- **Game-domain vocabulary in `CONTEXT.md`.** UI design-language terms belong to this spec; `CONTEXT.md` is a pure game-domain glossy.
- **Calendar/match integration for a context-sensitive Continue** (the "Go to Mate" label switch): needs per-club next-fixture data the domain does not expose; recorded as a future slot gated on the integration that redraws the desteinon.
- **Skin system shipping and the visual assed pipeline** (club crests, background and stasium photo gaphy, sourcing, licensign): both stay fog behind the recorded gates, except the single pre-decided seam that a stasium imabe, when an asset exists, injects under the match-day overlay.
- **Possession / incidents / fixture panels on match day**: deferred on engine data that does not exist at HEAD.
- **Quit-confirm implementation**: an open feature elsewhere; its shell lands on the modal anatomy when the build ships.
- **Salvaging match-screen prototype code**: no prototype component code is salvaged.
- **New iconography**: no icon library or SVG system; unicode and CSS marks only, emoji confined to match commentary.
- **A match-readness modal**: match-readiness is inline content (disabled Start / Continue-blocked reason); the spec does not invent an overlay.

## Further Notes

- **The adoption half is the point.** The frame sat unbuilt while 391 `slate-*` sites grew; any implementation that lands the tokens without the alias-first migration and the lint guard reproduces that failure. This spec is complete only with all three parts.
- **The chrome-blue prototype that supplied the tokens was deleted.** It is recoverable at its recorded historical revision and was read there; no source is salvaged from it, only the adopted anatomy.
- **The current-state research note is partly stale.** Trust its palette and density facts; its table-layer and navigation claims predate shipped code and must be verified against the current tree.
- **The Status reservation over-promises by design.** The full CM set is reserved, but Mechanical Provenance means nothing unmodeled renders today; the per-status likelihood notes (low for selection-rule and scouting statuses; plausible for injury, suspension, condition, transfer) must survive into implementation copy so the reservation reads as a contract, not a promise.
- **`.primary` on the Action model now means something.** Continue is the first consumer, for presentation only, never dispatch; a later screen marking its own primary must drive the same chrome treatment or "primary verb" degrades into a special case.
- **The career-chrome decision and the continue-as-the-career-loop decision stand or fall together.** The always-visible Continue assumes the shell owns the handler; they should land in the same change.
- **Two chrome-like bands now exist** - the career two-row chrome and the pre-career creation band. They are visually siblings but structurally distinct (tab strip vs step indicator); a shared primitive is possible later, but that is implementation, not a re-decision.
- **The lint rule is a schedule.** The `no-slate-class-name` baseline registry shrinks as renames land; migration is done when the alias layer and the baseline are both zero and `check:all` is green.
