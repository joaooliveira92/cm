Overview

The onboarding in Championship Manager: Season 03/04 was not a tutorial in the modern sense. There was no guided overlay, animated coach, checklist, or sequence of contextual tooltips. Instead, onboarding was a short configuration flow followed by immediate exposure to the full management interface.

The experience can be divided into two layers:

Explicit onboarding: starting or loading a game, choosing leagues, creating a manager, and selecting a club.
Implicit onboarding: learning the game by exploring the squad screen, opening menus, reading status abbreviations, and advancing time.

Contemporary guidance described the interface as familiar to players of earlier Championship Manager titles, but potentially daunting to newcomers because substantial functionality was presented almost immediately.

1. Startup and game-entry screen

After launching the game, the player first saw the Eidos and Sports Interactive splash screens. These could be clicked through, after which the game displayed its main entry screen.

Visual character

The opening interface followed the visual language of an early-2000s desktop application:

A full-screen or windowed application frame.
A football-themed photographic background or skin.
Rectangular, text-led controls.
Small typography intended for a 1024 × 768 display.
Strong reliance on beveled panels, shaded title bars, and conventional menu structures.
Little visual animation beyond transitions and loading behavior.

The game supported different skins, including a traditional skin and the smaller-font “Ter” skin. Its backgrounds could change when entering different screens, while a title-bar image or logo occupied part of the upper interface. The default full-screen target was 1024 × 768.

Primary options

The game-entry screen exposed actions such as:

Play Game
Resume Last Game
Loading an existing save
Starting or joining a network game
Accessing game options

The exact wording could vary slightly with version, language, or skin, but the important characteristic was that these appeared as a compact list of commands rather than as large illustrated cards.

The first decision was therefore functional rather than narrative:

Do you want to continue an existing career, create a new simulation, or use a quicker predefined starting point?

This screen did very little explaining. The player was expected to understand conventional commands such as “Play,” “Load,” and “Resume.”

2. Quick Start versus Start New Game

Selecting the game-starting path introduced an important choice between a Quick Start and a fully configured new game.

Quick Start UI

Choosing a Quick Start opened a comparatively small selection dialog containing a list of countries.

The UI was essentially:

A title indicating that a quick-start game was being loaded.
A vertically arranged list of available countries.
A highlighted row showing the current selection.
Confirmation and cancellation controls.

A Quick Start loaded a pre-created game with the selected country’s principal competition active. This reduced setup time but restricted the player to one active league and produced the same basic pool of available players whenever the same quick-start file was used.

Onboarding purpose

The Quick Start function acted as the closest thing CM 03/04 had to a beginner mode. It removed several technical decisions:

How many countries should be simulated?
Which divisions should be active?
What level of simulation detail should be used?
How much load could the computer handle?

However, the game did not frame Quick Start with beginner-friendly language such as “Recommended for new players.” It presented it as an alternative loading method.

3. Select Leagues screen

The complete new-game path led to the Select Leagues screen. This was the most technical part of the onboarding.

It was not a decorative map-based selector. It resembled a configuration utility or database setup screen.

Main UI structure

The central area contained a long list of footballing nations and their league configurations. A country could be activated and then configured to determine how deeply its league structure would be simulated.

Typical interface elements included:

Country or league names arranged in rows.
Selectable controls beside each country.
A way to choose the lowest active division.
Detail or simulation-mode settings.
A database-size selection.
A recommendation control.
A prominent Continue Game action.

The player could run several countries concurrently and choose the lowest level to simulate in each one. This made it possible, for example, to model England deeply while limiting another country to its top division.

“Full Detail” and background simulation

League rows could include a Full Detail setting. Selecting it instructed the game to model that competition using the recommended detailed simulation rather than a reduced background model. Contemporary players described the control as an option associated with each selected league.

CM 03/04 could also run a country in the background. In that state, most of its competitions were calculated with a less demanding simulation engine. This was especially important because hardware performance was an explicit part of the setup experience. Running a league in the background could significantly improve processing speed on weaker computers.

What the UI communicated well

The screen gave experienced players considerable control:

Breadth of the football world.
Depth of playable divisions.
Simulation accuracy.
Processing requirements.
Career mobility between countries.
What it communicated poorly

It forced a new player to make decisions before the player had enough experience to understand their consequences.

Terms such as:

“Background”
“Full Detail”
“Database Size”
“Lowest Active Division”

were system-oriented rather than user-oriented. They described how the simulation worked, but not necessarily what experience the player would receive.

A modern equivalent might say:

“You can manage clubs in these leagues.”

or:

“This league will be simulated but will not be fully playable.”

CM 03/04 generally expected the player to infer this distinction.

Recommended configuration button

The screen included a Select Recommended button. It evaluated the reported computer specification and selected what the game considered a suitable set of leagues. The recommendation was useful but not guaranteed to be accurate because it depended on the operating system correctly reporting the hardware.

This was an important onboarding device because it converted a technically complex screen into a near one-click choice. Nevertheless, the player could still manually alter the selections.

Continue and initialization

Once satisfied, the player clicked Continue Game.

The game then initialized the selected football world. This could take a noticeable amount of time, especially with many leagues or a large database. Rather than presenting a playful onboarding sequence during this delay, CM 03/04 treated it primarily as database processing.

The flow therefore felt like:

Configure simulation
↓
Commit configuration
↓
Wait for database construction
↓
Create manager

That ordering is significant. The game built the world before asking who the player would be inside it.

4. Add Manager screen

After league initialization, the player arrived at the Add Manager screen. This was the most conventional form-like portion of onboarding.

A surviving screenshot gallery explicitly identifies this setup stage as “Manager setup,” including the ability to choose a language appropriate to the team being managed.

Form layout

The interface was built around structured data-entry controls rather than character customization.

The player entered information such as:

Manager name
Date of birth
Nationality
Favored club
Spoken language or languages
Club to manage

The screen likely used a mixture of:

Text-entry boxes.
Drop-down selectors.
Scrollable lists.
Date fields.
Club-selection controls.
A final Continue Game button.

There was no three-dimensional avatar, portrait creator, wardrobe selection, personality quiz, or visual backstory builder. The “character” was defined almost entirely through database fields.

Information hierarchy

The manager’s identity occupied one section of the screen, while club selection occupied another. The design treated the person and the job as related pieces of a single form.

The fields had simulation consequences. Nationality and favored club influenced how the football world perceived the manager. A favored club could be more receptive, while rivals might respond less favorably.

This is an interesting piece of UI design because the form looked administrative, but its contents were not purely cosmetic. The game did not heavily dramatize those consequences. It trusted the label and external documentation to communicate their importance.

Club selection

Club selection was another information-heavy control. Rather than showing teams as large crests or cinematic stadium scenes, CM favored compact lists and database navigation.

A player would broadly:

Choose a nation or competition.
Navigate the available clubs.
Select a club.
Review the chosen assignment.
Continue into the career.

This made browsing efficient for users who already knew which club they wanted, but less welcoming for users who wanted the interface to help them discover an interesting team.

5. Arrival at the club

After clicking Continue Game, the player was taken directly into the main simulation. The first view was ordinarily the selected club’s Squad screen.

This transition was abrupt by modern standards.

There was no extended presentation such as:

A contract-signing cinematic.
A chairman welcoming the manager.
A guided tour of the facilities.
An assistant asking which responsibilities to delegate.
A mandatory tactical tutorial.
An onboarding checklist.

Instead, the visual message was:

Here is your squad. Begin managing.

6. The first Squad screen

The Squad screen was the real beginning of play and the point where implicit onboarding took over.

Overall composition

The interface resembled a dense information-management application. Its main components included:

Global navigation and header

Across the top or upper part of the screen, the player had access to persistent game controls and contextual information, including:

The current game date.
Navigation between recently viewed screens.
Broad game or manager menus.
A command for advancing time.
A contextual title identifying the current club, player, or section.
A title-bar image, logo, or club-related visual depending on the installed graphics and skin.

The game could associate backgrounds and title-bar images with clubs, players, stadiums, and specific screens. When no specialized image existed, it displayed a default background.

Contextual club navigation

The club area gave access to views such as:

Squad
Tactics
Training
Fixtures
Results
Staff
Finances
Information
Competition-related screens

The interface was hierarchical. Selecting a club established the context, after which related sections became available through menus or buttons.

Main data table

Most of the Squad screen was occupied by a scrollable table of players.

Rows represented individual footballers. Columns could show information such as:

Name
Playing position
Selected status
Fitness or condition
Morale
Appearances
Goals
Average rating
Value
Availability indicators

The exact columns could vary with the selected view.

The MobyGames gallery describes the immediate post-setup display as an “initial squad” and separately shows alternative squad information views, player profiles, contracts, search interfaces, training, formations, and instructions.

Status abbreviations

One of the most visually distinctive elements was the compact status marker beside player names.

At the start of a season, many players displayed Lmp, meaning “Lacking Match Practice.”

Other abbreviated indicators included:

Inj: injured
Sus: suspended
Wnt: wanted by another club
Bid: a transfer bid had been made
Yel: one yellow card away from suspension
Int: on international duty
Fgn: considered foreign under selection rules
Ine: ineligible
Wpm: no work permit
Tir: tired
Cup: cup-tied
Loa: available for loan
Lst: transfer-listed
Unh: unhappy
Unf: not fully fit
Sct: being scouted
Yth: on a youth contract
Req: transfer-listed by request

These labels were space-efficient and enabled experienced players to scan the squad very quickly. For beginners, however, they constituted a separate visual vocabulary that had to be learned.

This illustrates CM 03/04’s general onboarding philosophy:

Optimize the interface for long-term expert use, even if the first hour is difficult.

7. Learning through navigation

CM 03/04 did not lock features until the player completed introductory tasks. Almost everything was available immediately.

The player learned primarily through four interface behaviors.

7.1 Clicking rows

Player names were interactive data objects. Clicking a name opened the player’s profile.

This made the squad table both:

A report, and
A navigation system.

The user did not need a separate “View Player” button for every row. The interface expected the user to recognize traditionally clickable names or list entries.

7.2 Contextual menus

Player and club screens exposed an Actions menu. This gathered commands relevant to the current object.

For a player, the menu could contain functions such as:

Make a transfer offer.
Scout the player.
Compare the player.
Change squad status.
Offer a contract.
Release a media story.
Set transfer or loan availability.

The comparison workflow, for example, used recently viewed player profiles. The user could open several profiles and then select Compare With from the actions menu, where incompatible comparisons could be greyed out.

This was powerful but discoverability was limited. Many features existed one or two levels inside textual menus.

7.3 Switching views

A screen frequently offered multiple data views rather than presenting everything simultaneously.

For example, a squad might be viewed according to:

General information.
Contract data.
Fitness.
Form.
Transfer status.
Selection status.

This reduced horizontal overcrowding, but required the player to understand that the same list could be reconfigured.

7.4 Advancing time

The principal rhythm of the game was controlled through Continue Game.

This button or date-area control functioned as the simulation’s primary call to action. When pressed, the game processed events until it encountered something requiring attention.

On match days, the date field could change to Go to Match, indicating that the current team selection would be used for the upcoming fixture.

That contextual label change was one of the game’s more elegant onboarding mechanisms. Instead of explaining the calendar model through a tutorial, the central action changed according to the state of the simulation.

8. News as an implicit task manager

Although the Squad screen was the first club view, the game’s news system became the main channel for presenting work.

Messages could inform the player about:

Injuries
Transfer offers
Contract developments
Player complaints
Media speculation
Scouting reports
Match preparation
Board expectations
Competition events

The screenshot collection emphasizes the role of media speculation, injury messages, grievances, coach reports, club reports, live cup draws, confidence information, and transfer activity.

UI behavior

A news item was not merely text. It could include:

A headline.
A dated message body.
Clickable player or club names.
One or more response buttons.
A link to a related profile or report.
Decision options embedded in the message.

This turned the inbox into a reactive form of onboarding. Rather than telling the player in advance how every system worked, the game waited for an event and then displayed the relevant decision.

For example, an unhappy player might produce a news item with several possible responses or promises. Media speculation could prompt the manager to comment on whether a player was available for transfer.

The news interface therefore operated as a just-in-time decision surface, though not necessarily as a just-in-time tutorial.

9. Tactics and training as the next onboarding steps

Once the player had inspected the squad, two interfaces naturally attracted attention: Tactics and Training.

Tactics screen

The tactics interface combined a graphical football pitch with conventional menus and setting panels.

Its principal UI elements included:

A pitch diagram.
Player positions represented spatially.
Formation or tactical-template controls.
Team-selection indicators.
Menus for team and individual instructions.
Set-piece and captain-selection functions.
Quick-load options for standard formations.

A beginner could load a familiar formation such as 4-4-2 or 4-3-3 using a tactical template, then modify it.

The screenshot gallery separately identifies screens for:

Formation
Team instructions
Player instructions

This separation was important. The main pitch gave a spatial overview, while detailed tactical behavior was configured through textual options.

Training screen

Training used a weekly schedule rather than a simple intensity slider.

The screen represented:

Days of the week.
Training sessions or activities.
Assigned coaches or physiotherapists.
Player groups or schedules.
Training-performance ratings.
Indicators showing improvement or decline.

The overview displayed players with star-based training ratings, while arrows indicated whether attributes in the displayed training area were rising or falling.

This was visually informative but cognitively demanding. The user was shown the full scheduling system rather than being led through a simplified first-week setup.

10. Visual design language
    Dense rather than spacious

The UI prioritized the amount of visible information. It used:

Small fonts.
Tight row spacing.
Numerous columns.
Compact buttons.
Abbreviations.
Text menus.
Scrollbars where necessary.

The game could be forced into 800 × 600, but documentation warned that it was designed for a higher resolution and that the smaller display would introduce scrollbars on many screens.

Skin-based appearance

The visual shell was customizable. A skin influenced:

Font size.
Panel colors.
Button styling.
Background treatment.
Placement or presentation of title-bar imagery.

Background images could be context-sensitive, with different images for a club, player, stadium, or particular screen. Otherwise, the interface could rotate through default football photographs.

Limited use of iconography

Icons and color were generally used to augment text, not replace it.

A status might have a visual marker, but it was also represented by a compact abbreviation. A player comparison could use color to indicate which player was superior in a particular attribute, with brighter variants for especially large differences.

This produced an interface that was visually restrained but semantically dense.

11. What the onboarding felt like

From a UX perspective, CM 03/04’s onboarding can be summarized as:

Launch
→ Choose a game-start method
→ Configure the simulation
→ Create a database-defined manager
→ Choose a club
→ Enter a complete professional management interface
→ Learn by inspecting, clicking, reading, and advancing time

Strengths
Fast for returning players: minimal ceremony before reaching the squad.
Highly configurable: league depth and database scope were controlled from the beginning.
Consistent interaction model: lists, profiles, menus, filters, and contextual actions worked throughout the game.
Expert efficiency: abbreviations and dense tables allowed rapid scanning once learned.
Clear core rhythm: inspect information, make decisions, and press Continue.
Context-sensitive progression: the Continue control changed to Go to Match when appropriate.
Weaknesses
High initial cognitive load: league simulation settings appeared before the player understood their consequences.
Little progressive disclosure: most management systems were available immediately.
Weak terminology support: abbreviations and simulation terms depended on manuals, guides, experimentation, or prior experience.
Few explicit next steps: the first Squad screen did not provide a structured first-day checklist.
Limited feature discoverability: powerful functions were often contained in textual action menus.
Performance configuration was exposed to the player: new users had to understand the relationship between leagues, database size, simulation detail, and processing speed.
Final assessment

Championship Manager 03/04 treated onboarding as entry into a professional tool, not as a staged introduction to a game.

Its UI communicated that the user was operating a large football database:

The new-game flow resembled simulation configuration.
Manager creation resembled completing an employment form.
Club arrival resembled opening a personnel-management application.
Learning occurred through tables, menus, news messages, contextual buttons, and repeated use.

The result was initially intimidating but exceptionally efficient after familiarity developed. Instead of hiding complexity, the interface exposed it and expected the player to build a mental model over time. That approach is a major reason the game could feel difficult during the first session but remarkably direct during a long-term career.
