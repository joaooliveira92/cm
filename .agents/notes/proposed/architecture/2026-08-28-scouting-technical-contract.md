# Agent Note: Scouting technical contract — events, Club Decider extension, RPC surface

Status: proposed

## Problem

With the Scout resource/assignment model ([Scout resource & assignment model](2026-08-28-scout-resource-and-assignment-model.md), `../feature/`) and the Progress/Attribute-Range formulas ([Progress accrual & Attribute Range computation](../feature/2026-08-28-progress-accrual-and-attribute-range.md)) settled, the Scouting milestone needs a concrete wiring: what events the Club Decider (the shared club-scoped stream already carrying Contracts/Budgets) emits, how Scouting Progress actually advances over time given Matchdays reset every Season with no multi-season rollover implemented, what read models serve the new Scouting screen and the Attribute-Range-aware Transfers screen, what RPC methods the renderer calls, and what invariants the Club Decider enforces for Scout assignment.

## Proposal

**Progress advancement is event-driven, not computed-on-read.** Matchday numbering resets to 0 every Season (`season.current_matchday`, bounded 1–38) with no global monotonic axis across Seasons yet, so a "stored assignment-start Matchday, diffed against now" scheme has no stable reference across a Season boundary. Instead, Scouting Progress is a **stored value**, incremented at a fixed hook point that already exists: the `boundary.type === "matchday"` branch of `advanceCalendar` (`season.ts:482-498`), which fires on every Matchday regardless of Season end. Right after `MatchdayResolved` is appended, a new step scans every club's active Scouting Assignments and appends one `ScoutingProgressed` event per club (batched, not one event per assignment — `{matchday, progressed: [{playerId, progress}]}` — mirroring `PlayerDeveloped`'s "one event per club per Season, all players inside" shape rather than growing the stream one event per assignment per Matchday), directly `UPDATE`-ing each `scouting_progress` row by the tuning increment, clamped to 100. Progress itself stays a persisted fact — the map's own Notes already call it out as "the one genuinely new persisted primitive this milestone introduces" — while the *narrowing formula* that turns Progress into an Attribute Range stays derived-on-read (ADR-0001 posture), computed in `packages/shared` and never itself stored.

**Two new tables, because their lifecycles differ.** `scouting_assignments (clubId, playerId)`: a row exists only while a Scout is actively assigned; deleted on `UnassignScout`. `scouting_progress (clubId, playerId, progress)`: a row persists across pause/resume/reassignment (Progress "just stops/resumes," per the resource-model note — no separate paused status), and is only deleted when the target Player joins the human's own squad. Collapsing these into one table would force a nullable "is this active" flag alongside a value that must outlive the row's own deletion, which doesn't hold together.

**Commands mirror `setTrainingFocus`.** `AssignScout(playerId)` / `UnassignScout(playerId)` follow the existing shape: `withExistingSave` → `assertSaveNotSacked` → `loadUserClub` → validate invariants → `sql` upsert/delete on `scouting_assignments` → `nextStreamSeq("club", club.id)` → `appendStreamEvents("club", club.id, seq, [{tag: "ScoutAssigned" | "ScoutUnassigned", payload: {playerId}}])` → return a view. `AssignScout` rejects (as explicit `Schema.TaggedError`s, never a silent no-op, matching this codebase's existing style) when: the club is already at its Scout-count cap (`scoutCountForTier(statureTier) `, a pure `packages/shared` function evaluated live — no persisted snapshot table, since Scout count has no spend-down state to track, unlike Transfer/Wage Budget), the target Player is already on the human's own squad (always Fully Scouted, not a valid scouting target), or the target Player already has an active assignment from this club. `UnassignScout` rejects if no active assignment exists for the pair, rather than silently succeeding. Every check is an app-level comparison inside the command function (a live count/lookup before the `sql` write), not a DB constraint or trigger — consistent with how Wage Budget's cap is checked today.

**Discard-on-own-squad-join is a direct call, not a subscribed reaction.** When a Player joins the human's own club (the `PlayerSigned`/`PlayerTransferredIn` append sites in `transfers.ts`), a `discardScoutingProgress(clubId, playerId)` call is inserted at that same site, deleting the `scouting_progress` row (and any `scouting_assignments` row). This matches the codebase's existing in-process synchronous reactor style (`developPlayersForSeason` called directly from `advanceCalendar`, no outbox/policy bus, per ADR-0007) rather than introducing a subscribed-handler abstraction for a single call site. Progress is left untouched when a Player moves to a different non-human club — the manager was learning about the player, not the contract.

**Read models: extend `MarketPlayerView`, add `ScoutingScreenView`, no new Player Detail view.** No per-attribute detail view exists anywhere today for market players (the Transfers screen list is the only surface, and it only ever showed `overallRating`/`transferValue`, never a per-attribute breakdown, not even for own-squad players). `MarketPlayerView` (`schemas.ts:434-444`) grows two nullable fields: `overallRatingRange` and `transferValueRange` (each `{low, high}`, `null` when Fully Scouted — render the exact `overallRating`/`transferValue` instead), computed server-side in `toMarketPlayerView` from the stored `scouting_progress` value via the shared noise-band formula, so the renderer never re-derives domain math. Full per-attribute Attribute Range (individual Attributes, Potential Ability, Injury Proneness) is **computed but not exposed** through any RPC/schema this milestone — the formula exists in `packages/shared` because Transfer Value's range needs it as an input, but nothing renders it standalone; a Player Detail screen that would consume it is out of scope (see map's Out of scope). The new Scouting screen is served by `ScoutingScreenView { scoutCount, assignments: [{playerId, playerName, clubName, progress}] }` via a new `getScoutingStatus` RPC; the screen's "assign a Scout to a Player" search reuses the existing all-players data source (`loadAllPlayersEcon`) already powering the Transfers screen, not a bespoke query.

**RPC surface**: `assignScout`, `unassignScout`, `getScoutingStatus` added to `AppRpcs` (`packages/contracts/src/rpc.ts`), following `setTrainingFocus`'s payload/success/error shape; views and errors defined in `schemas.ts`; handlers wired into `rpcServer.ts` one arrow function per method, same as every other command.

## Alternatives considered

- **Computed-on-read Progress** (`Matchdays elapsed since assignment start minus paused spans`, no per-Matchday event) — the map's stated architectural default ("derived on read," ADR-0001) and the first option this ticket's Question posed. Rejected specifically for Progress: Matchday numbering resets every Season with no multi-season rollover built yet, so there is no stable time axis to diff a stored start-point against once a Season boundary is crossed. A stored, incremented value sidesteps needing that axis entirely.
- **One `ScoutingProgressed` event per (club, player) pair per Matchday** — rejected: grows the club stream by one event per active assignment per Matchday, when a single per-club batched event (mirroring `PlayerDeveloped`) carries the same information.
- **Single `scouting` table merging assignment and progress** — rejected: the two facts have different lifecycles (assignment is transient, deleted on unassign; progress is durable, surviving pause/resume), and merging them forces a status flag alongside a value that must outlive the row's own deletion.
- **Snapshot Scout count into a table at Season start** (mirroring `club_budgets`) — rejected: Transfer/Wage Budget are snapshotted because they carry spend-down or running-total state within a Season; Scout count is a pure cap with nothing to track between reads, so deriving it live from Stature Tier needs no persistence.
- **New Player Detail RPC/view to carry per-attribute Attribute Range** — rejected for this milestone: nothing today renders a market player's individual attributes, exact or ranged; building a detail surface just to show Attribute Range would be new scope the destination didn't ask for. The formula is still implemented (Transfer Value's range depends on it), just not wired to a query.
- **Subscribed policy/handler for the discard-on-own-squad-join reaction** — rejected: this codebase has no outbox or policy-bus abstraction (ADR-0007); a direct function call at the existing `PlayerSigned`/`PlayerTransferredIn` append sites matches every other cross-cutting reaction in the code (`developPlayersForSeason`, `judgeSeasonEnd`).

## Acceptance criteria

- `scouting_assignments` and `scouting_progress` exist as separate tables; `AssignScout`/`UnassignScout` commands append `ScoutAssigned`/`ScoutUnassigned` to the club stream and keep `scouting_assignments` in sync.
- The `MatchdayResolved` branch of `advanceCalendar` appends one batched `ScoutingProgressed` event per club with active assignments and increments each `scouting_progress` row, clamped to 100.
- `AssignScout` rejects at Scout-count cap, against an own-squad target, and against a duplicate assignment; `UnassignScout` rejects when no active assignment exists. All three checks are app-level, evaluated live, no DB constraints.
- Joining the human's own squad deletes the Player's `scouting_progress`/`scouting_assignments` rows via a direct call at the transfer-completion site; moving to another club leaves Progress untouched.
- `MarketPlayerView` carries `overallRatingRange`/`transferValueRange` (nullable), computed server-side; no per-attribute range is exposed via any RPC this milestone.
- `assignScout`, `unassignScout`, `getScoutingStatus` exist on `AppRpcs` with `Schema.Class` views/errors in `schemas.ts` and handlers in `rpcServer.ts`.

## Risks

- Deriving Scout count live from Stature Tier assumes Stature Tier itself doesn't shift mid-Season in a way that would retroactively invalidate an already-full assignment set; if Stature Tier ever becomes Season-volatile, `AssignScout`'s live cap check could reject/accept inconsistently with a stale renderer view, and Scout count may need to become a stored per-Season snapshot after all.
- Progress as a stored, incremented value (rather than computed-on-read) means a missed or double-fired `MatchdayResolved` hook desyncs Progress from actual elapsed Matchdays with no way to recompute it from history other than replaying the event log — accepted because the codebase already treats the event log as non-authoritative for serving reads (ADR-0007), and `MatchdayResolved` is a single, already-relied-upon hook point.
- Leaving per-attribute Attribute Range unexposed means the formula's correctness is only exercised indirectly (through Transfer Value's range) until a Player Detail screen consumes it directly — a latent risk that the formula's per-attribute behavior goes unverified in the UI until that future screen exists.
